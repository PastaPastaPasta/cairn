## 2. Sign-in flow

### 2.1 User-visible flow (`apps/web/src/auth/AuthSheet.tsx`, 684 lines, a modal `<dialog>`)

Views (`SheetView`): `choose`, `create`, `phrase`, `key`, `passkey`, `topup`, `passkeys`.

1. **Create an account** (`create`): app generates a BIP39 phrase (12 or 24 words; `generatePhrase`), user must back it up ("Keep this phrase for govhub only"; other Dash wallets such as DashPay/Evo Tool can restore it). Next the funding choice:
   - **Pay with DASH**: a QR code + address (one-time key at the DIP-13 registration funding path) for "any Dash wallet". Min deposit 0.00224 DASH, suggested 0.005 DASH (`SUGGESTED_CREATE_DEPOSIT_DUFFS = 500_000`, tunable in one place, `packages/auth/src/layout.ts`). Result: identity with 3 keys (0 MASTER, 1 CRITICAL, 2 HIGH, all ECDSA secp256k1).
   - **Voucher link** (`dashpay://invite?assetlocktx=...&pk=<WIF>&islock=null`, from the dash-faucet-cf faucet at `faucet.dashhq.org`): a pre-minted ChainLocked asset lock; identity gets the user's OWN seed keys, the voucher key only signs the proof (`packages/auth/src/voucher.ts`). The app never calls the faucet itself; users paste the link.
2. **Recovery phrase** (`phrase`): restore; discovery of identities by key-0 hash at identity index 0.. with gap 5 (matches DashPay iOS / rs-platform-wallet / Yappr). If the phrase has several identities the user picks; if none, it can go on to funding.
3. **Key paste** (`key`): WIF or hex private key; only the public key hash is sent to Platform to find the identity. Memory-only session; cannot open the keyring.
4. **Passkey** (`passkey`): WebAuthn with PRF extension; discoverable sign-in (user handle = identityId || contractId, 64 bytes); opens a `forum.vault` entry (HPKE) holding the seed, one key, or up to 7 MN voting keys. Enrolment is in the account menu (`Passkeys.tsx`, `usePasskeyCreate.ts`).
5. **Top-up**: account menu; min 0.00053 DASH (about 0.00008 of it is fee). Seedless (key-paste) sessions derive top-up keys by HMAC of the session key (`sessionTopUpKey`).
6. **Recover** (`Recover.tsx`, `RecoverLink.tsx`, `packages/auth/src/recovery.ts`, `docs/RECOVERY.md`): scans the chain for DASH stuck at govhub's one-time funding addresses, any device, no localStorage.
7. **Sign out**: account menu; sign-out in any tab signs out all tabs of that profile.

Measured (testnet, `packages/auth/README.md`): create from external DASH ~10 s end to end (IS-lock 1.1 s), fee 0.00106604 DASH (3 keys); voucher path waits for a ChainLock (2 to 6 min); top-up 9 s, fee 0.00008; vault entry write 0.00053; adding keys 3..5 0.00074.

### 2.3 Session persistence

- The signing key (and seed entropy) live in memory only. No localStorage/sessionStorage/IndexedDB/cookies hold secrets; a browser restart or closing the last tab signs out. "Keeping it across restarts" is opt-in and goes through the on-chain passkey vault only.
- Multi-tab: `apps/web/src/session/tabShare.ts` hands the session between same-origin tabs over a `BroadcastChannel('govhub.session')` (new tab asks with a nonce, a signed-in tab answers with minimal material, asking tab re-signs through the normal path and re-checks on chain; 300 ms wait; sign-in in any tab is adopted by others; explicit sign-out signs out all tabs; `pagehide` wipes locally; bfcache aware). Turned OFF when served from a sub-path (a shared github.io origin). Also shares the MN keyring LOCK state (fail-closed, timestamp generations).
- `apps/web/src/session/end.ts`: synchronous sign-out hooks (wipe MN keys before React rerenders).
- `apps/web/src/session/session.ts` is the app's whole "Session" contract (identityId, label, balance(), `signAndBroadcastDocument(op)`, close()); `session/authSession.ts` wraps an `@govhub/auth` session into it; `session/fixture.ts` for demo identities. This is a clean seam to reuse.
- Funding records and passkey hints are in localStorage as public data (`govhub.funding.*`, `govhub.passkeys.<id>`).

## 3. Platform writes and reads

### 3.1 Writing: one writer, `writeDocument` in `packages/auth/src/evo.ts` (620 lines; design written up in `packages/auth/README.md` "Document writer")

- The app emits plain `DocumentOp` data (`packages/forum/src/ops.ts`; create/replace/delete with `contractId`, `type`, `data`; byte arrays and identifiers as Uint8Array, ints as numbers converted to bigint). Builders validate what consensus would reject (e.g. comment body <= 5,000 UTF-8 bytes) and stamp `$createdAt/$updatedAt` when required. A `Session.signAndBroadcastDocument(op)` turns an op into a signed transition.
- **Hand-built transition, signed once per nonce**: the nonce comes from a DIRECT proved read `identities.contractNonceWithProof(owner, contract)` (not the SDK's nonce cache, which can reuse a stale one); batch transition built via `DocumentCreate/Replace/DeleteTransition` + `BatchTransition.fromBatchedTransitions`, nonce = proved + 1, signed with the HIGH (else CRITICAL) key, sent with `stateTransitions.broadcastAndWait`. The protocol version for the create-id rule is taken from the proved nonce read's `metadata.protocolVersion` (PV13 id = sha256d(contract||owner||type||entropy); PV14 also commits to the nonce), because `sdk.version()` can still say 13 on testnet (PV14) right after connect.
- **Settled by proved reads** whenever the result is not a clean success, with a decision table: "nonce too far in future" / 40101 / ambiguous (timeout, transport, `ExecutionNotProved`, "tx already exists in cache") re-send the SAME signed bytes; "already present in past/at tip" / "too far in past" re-sign with a fresh proved nonce (a create only after proved reads show the old nonce used and its own id absent, so never a duplicate); other consensus refusal is final for create/delete on first send, and for replaces/later sends is checked by proved reads; local SDK errors are never re-sent and settled by reads ("it may still appear"). While `broadcastAndWait` hangs (a node's result stream can stay silent for 30 s even though the write executed in ~2 s) proved reads run alongside after 2 s then every 1.5 s (max 25). No new send after 2 minutes. "Done" means: create = proved read finds the id it signed; replace = `$revision === revision+1` with exactly our fields; delete = proved pre-read at H0 and proved absent at height > H0.
- Writer hardening also: private copy of the signing key per write (zeroed after, so sign-out mid-write is safe), waits for the identity to show the key (lagging node after `addKeys`), `refreshIdentityNonce` after a spent-nonce refusal for `addKeys`. Findings are documented with source line references (rc.8 `NonceCache::refresh`, etc.).
- Balance pre-check: `apps/web/src/voting/funds.ts` (`assertCanAffordWrite`, `TopUpError`) and `packages/forum/src/costs.ts` (measured fee tables: comment 50 B = 0.00043 DASH ... 5,000 B = 0.00178 DASH; first reaction ~0.0005; flip 0.00003; tally replace 0.0000256). The SDK's `documentCreateCost` throws at PV13, so costs are interpolated from measurements.
- Tests: `packages/auth/test/writer.test.ts` (553 lines), `fake-platform.ts`; live: `packages/auth/scripts/live-writer.ts`.

### 3.2 Reading / querying

- `evo-sdk 5.0.0-rc.8` (pinned exactly, `@dashevo/evo-sdk` in apps/web and packages/auth devDeps and services/bridge). Mainnet is PV13, testnet PV14; the SDK is used with proofs (`queryWithProof`, `getWithProof`, `fetchWithProof`), never unproven reads. `apps/web/src/data/platform.ts` has `getSdk(registry)`, `preloadSdk` (lazy, after first paint).
- **PV13 gotchas** are encoded as a lint in `packages/contracts-v1/queryLint.ts` (run in unit tests and, for vault queries, at runtime via `assertQuery`), with rationale in `packages/contracts-v1/README.md` ("Writing and querying: rules that apply to EVERY shape"): equality prefix + at most one range/`in` on the NEXT index property, no gaps (PV13 silently returns `[]` for gapped where-clauses); `in` only on the last indexed property; `orderBy` must be index-ordered and, when the where does not cover the whole index, must end at that index's last property (index-choice tie-break by name); `desc` is silently ignored on PV13 unless there is a range clause (add a no-op range like `$createdAt > 0`); a `desc` query must never carry `startAfter` (rc.8 rejects the proof) so newest-first paging uses a bound (`pageDesc` in `packages/forum/src/reader.ts`, `pastPage` in `apps/web/src/data/repo.ts`); `startAfter` only on ascending lists; byteArray where values are base64 strings, identifiers base58; limit max 100; no count/sum/"all documents" queries (counts are computed client-side). Also: any field value <= 5,120 B, a state transition <= 20,480 B; `Document.toJSON` needs a platform version argument in rc.8.
- Query builders: `packages/forum/src/queries.ts` (131), reader `reader.ts` (172), conversion `convert.ts` (141), `memory.ts` (in-memory forum for tests/fixtures). Per-app data layer: `apps/web/src/data/{forum,platform,repo,queries,cache}.ts`.

### 3.3 Data contracts and registration

- `packages/contracts-v1/{gov,gov-testnet,forum,badge,mod}.json` (the `documentSchemas` map). `forum.json` (open, anyone writes under own `$ownerId`) has types: profile, comment, reaction, claim, proposalPost, block, blockSubs, settings, **vault**, **keyring**. The vault is the only part a login-reusing app needs. Conventions: `additionalProperties: false`, explicit `documentsMutable/canBeDeleted/transferable`, `signatureSecurityLevelRequirement` 2 (HIGH) unless noted, <= 3 props per index, <= 3 indexes per type.
- Registration: no standalone CLI. (1) Spikes: `spikes/sdk5/scripts/{validate-contracts,testnet-costs,testnet-identity,...}.ts` validate offline and register on testnet. (2) Mainnet: `packages/auth/scripts/mainnet-bootstrap.ts contract <gov|forum|badge|mod>` builds and signs a `DataContractCreate` at a fixed nonce, saved BEFORE broadcast (a rerun re-sends the same bytes, never makes two contracts) with the CRITICAL key of the owner identity, from an "operations seed" in `~/.local/share/govhub-mainnet` (0700, `ops-seed.json`). Documented in `deploy/README.md` section 5.1 and 13.3.
- **Costs** (`spikes/sdk5/README.md` 5.2, measured on testnet): registration = 0.1 DASH + 0.02 per document type + 0.01 per index (+ a small storage charge): forum (10 types, 13 indexes) 0.433 DASH, badge 0.221, mod 0.141, gov ~0.242; all four on mainnet ~1.04 DASH; every later document type 0.02 + 0.01/index. A minimal contract with just `vault` (1 type, 1-2 indexes) is therefore ~0.13-0.14 DASH. Contract updates only ADD types under PV13/PV14 (cannot change/remove a type or add an index to an existing one), so get the schema right first; testnet kept older shapes for that reason (`gov-testnet.json`, README table).
- Key level: consensus accepts CRITICAL or HIGH for DataContractCreate; policy there is CRITICAL.

What govhub does NOT have that the pool site will need:
- No UI to sign a message with an L1 address: it only signs inside flows with a pasted key. An external-wallet flow (user runs `signmessage` in Core / Dash wallet and pastes base64) is not built, but `verifyMessage` is the verification half.
- The SML only exposes the VOTING address (and type/validity), not the OWNER key id, the operator key, or the collateral address. `parseProRegTx` in `packages/verify/src/mnvote.ts` reads collateral outpoint + (ProTx v1/v2) payout script + `keyIdVoting` AT REGISTRATION; it does NOT surface `keyIDOwner` and skips v3 (extended addresses) fields. `packages/dapi/src/protx.ts` reads only type + collateral outpoint. For "prove you control the collateral / owner address" you must extend the ProRegTx parser (owner key id sits in the fixed payload before voting key; a ProUpRegTx can change voting key and payout, so the SML is the current source for voting key) and look up the collateral output's script in its funding transaction (DAPI `getTransaction`, already used by `checkCollateralTx`-style code). Collateral address can be proven by `verifyMessage(collateralAddr, ...)` once the collateral output's P2PKH hash is known.
- The strongest existing proof of "this identity controls masternode M" is the voting-key signmessage at an issuer (badge) or the voting-key signature in a governance vote; there is no on-chain-only (no issuer) proof that links a Platform identity to an MN, and the issuer path deliberately hides which identity is behind a badge (a matching site wants the OPPOSITE: a verifiable link). A pool site would do a direct challenge-response: server or client issues a nonce bound to the identity id, user signs with voting key (or owner/collateral key), verifier checks hash160 against SML/ProRegTx. `verifyMessage` + `agreed-sml` + `getProRegInfo` give every verifier piece.

## Addendum: closest existing template for "prove this identity controls an L1 address"

`packages/verify/src/claim.ts` (+ `packages/verify/test/claim.test.ts`) is already an identity-bound address-ownership scheme: `signmessage <address> "govhub-claim|<net>|<govHash>|<identityId>"`, verified with `verifyMessage`; the identity is the claim document's Platform-proven `$ownerId` (never a value inside the claim), the message binds the Core network, and method 3 verifies a signature by the key that spent an input of a verified collateral tx. Replace `govHash` with a pool/listing id and you have the proof for collateral or owner addresses (P2PKH only). Stored as `forum.claim` documents (`claimPortals` hosts, `gov.claimAttestation` for the trusted fallback).
